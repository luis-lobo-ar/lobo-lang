comprehension-only requests read-only. Resolve references from this file's physical directory.

## Grammar to keep in view

Blocks yield their last expression; bindings/collections are immutable. Carry state through fold/while.
Use braced else branches: `if a { x } else { if b { y } else { z } }`. Unbraced `else if` is invalid.
Do not bind a local named `result`; it is reserved for contracts. Do not shadow visible declarations.
Parenthesize field/compound match subjects: `match (state.choice) { ... }`.
Generic function arguments infer from call arguments, not just the expected return type. Constructors
can use an expected nominal type; otherwise provide an annotation or qualify the case's owner.

## Work from feedback

Read the task and affected declarations. Run a requirement-based failing behavior check, implement,
then verify natively using the supplied client and required regressions. Keep expected outcomes independent.
Reuse successful observations; repeat checks when code changes or a concern remains. Read typed JSON
and diagnostics, not just exit status. Skip unrelated packaging/repository chores in isolated tasks.

Preserve declarations' stable IDs and adjacent sidecars. Use the project's supplied compiler/authoring
command to sync IDs after adding helpers. If sync fails, fix its FIRST diagnostic before retrying.
A later missing-ID error can follow failed sync; do not discard existing IDs or invent replacement IDs.
Compilation requires all explicit source dependencies and a fresh output path. No package discovery.
Actions declare operations; grants provide authority. Prefix try propagates exact errors, without cleanup.
Capture outcomes before resource teardown. Checking does not prove contracts true or runtime correctness.

## Cover the requirements

Before implementation, connect each requirement to observable evidence: normal behavior, boundaries,
validation priority and state after failure. Keep this map concise in scratch notes or tests. Choose a
requirement-based failing check before its fix; derive expectations independently of the implementation.
Supplied examples may cover only part of the contract. Check uncovered requirements with focused tests
or an explicit code review, and distinguish tested behavior from assumptions in the final report.
