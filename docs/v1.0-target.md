# Lobo v1.0 target

Status: broader product/workspace target, not a claim about current support. The separately authorized
[bounded language 1.0 release](../decisions/0033-bounded-language-1-release.md) does not imply completion
of this workspace target. Core 0.12 development implements the four language families and passes the fixed
programs/changes. The [language release receipt](../benchmarks/results/2026-11-04-language-v1-release.json)
records final package/check status for language 1.0. Host services/workspace tools remain future work.

## Intended outcome

An agent can enter a Lobo workspace, discover its available tools and authority, obtain relevant program
context, make a bounded semantic change, verify it, and submit an evidence-bearing revision. A human can inspect
the resulting behavior, authority, uncertainty, and reason for acceptance.

The first Core compiler establishes language behavior on which this workflow can depend. It is a foundation
for the semantic workspace; its temporary expression-tree artifact is not the final product boundary.

## v1.0 capabilities

| Area | Required outcome |
| --- | --- |
| Language | Versioned grammar and semantics for an explicitly advertised useful subset |
| Representation | Canonical program graph with stable entity identity and specified interchange |
| Compiler | Checked lowering and a supported execution target with conformance evidence |
| Contracts | Precise runtime/static status and revision-bound evidence without overstated guarantees |
| Actions | Declared resource interactions and host-enforced capability scopes |
| Tooling | Discoverable typed operations, structured diagnostics, cancellation, and bounded output |
| Workspace | Atomic transactions, revision-consistent reads, recovery, and semantic diffs |
| Context | Attributable packages with governing rules, sensitivity controls, and explicit omissions |
| Coordination | Isolated agent changes and conflict analysis against shared semantic constraints |
| Review | Deterministic readable projections of contracts, changes, actions, and remaining obligations |
| Reproducibility | Pinned dependencies and identified compiler, environment, artifacts, and evidence |

The release must specify its language subset before declaring conformance. Breadth of syntax, a custom VM,
or compiling the compiler in Lobo does not substitute for these outcomes.

## Evidence for release

Mandatory suites must pass on the exact release revision without unexplained skips. Protocol/schema tests,
graph round trips, runtime capability checks, transaction recovery, and the supported compiler conformance
suite must all have recorded results. Claims of static proof must name the method and assumptions.

Evaluate representative agent feature, repair, refactor, and conflicting-change tasks against a documented
file-and-shell baseline. Predeclare the workload, quality criteria, and meaningful improvement threshold before
the experiment. Report cost, correctness, context use, unrelated changes, and reviewer effort, including tasks
where Lobo performs worse. The design can change if this evidence fails to support its central hypothesis.

## Current boundary

Core v0.9 provides scalar/text/byte/record/variant/list functions, explicit closed module linking, state-driven iteration, exhaustive matches and typed failure values, checked action bounds,
counted folds, stable declaration IDs, source checking, native
machine-code compilation, runtime contracts, structured CLI output, native/reference differential tests,
and a fuel-limited reference evaluator. Compiler source diagnostics and the maintained VS Code extension
support development. Action bounds are conservative metadata. Language 1.7 separately supplies a closed
native OS slice with explicit launch grants; the broader workspace authority model below remains proposed.
It does not yet provide canonical graph interchange, the daemon, context retrieval,
host actions, WASM generation, semantic transactions, or foreign-library bindings.

## Practical solution-readiness gate

The current priority is the separate [language-completeness milestone](language-completeness.md): express
representative computational programs first, with ecosystem integrations later. The application/library
requirements below remain future readiness criteria, not prerequisites for that language-only milestone.

The user wants an explicit notice when Lobo can implement a useful end-to-end solution. This is a practical
milestone separate from the full agent-workspace v1.0 target and from claiming a language is universally
"complete". The first target solution still needs to be selected; do not silently assume that a scalar
algorithm, file-processing tool, and web service have the same prerequisites.

Acceptance requires one identified solution built in Lobo, compiled to a native binary, tested against its
requirements, and developed with matching editor support. Required libraries are part of readiness, not
optional polish. Depending on the target, this includes strings/bytes, collections/structured values,
serialization, communications, storage, and search. These libraries are not currently implemented.

Third-party reuse should be evaluated before building replacements. A C-compatible FFI with reviewed Rust/C++
wrappers is a candidate native path, not current support. Specify types/ABI, buffers, ownership/lifetimes,
errors/unwinding, callbacks, cancellation, link/runtime dependencies, and library identity before implementation.
Python/Node integrations are separate optional runtime bridges, not automatically standalone native linking.
See [Rust's FFI guidance](https://doc.rust-lang.org/nomicon/ffi.html) and
[Python embedding](https://docs.python.org/3/extending/embedding.html) for the corresponding runtime boundaries.

Before admitting resource-access or external libraries, the target needs a specified and tested security model:

- Explicit actions and narrow resource capabilities, with host-owned grants and no ambient authority.
- Application policy bounds what can be granted; modules/functions declare requirements and receive only
  explicitly delegated subsets. Imports and libraries cannot broaden authority implicitly.
- Host enforcement for resource scopes, rate/burst limits, concurrent operations, deadlines, cancellation,
  memory, and byte budgets. Retry charging, hierarchical/shared quotas, revocation, and failure codes need definitions.
- Reviewed native trust boundaries. FFI annotations and wrappers alone cannot contain arbitrary native code;
  brokered operations and suitable OS/process isolation may be required to prevent direct-call bypasses.
- Pluggable logging, audit, and trace interfaces with event schemas, correlation/revision identity, privacy
  redaction, backpressure, and explicit failure policy. Mandatory audit evidence must not silently become optional
  logging when a sink fails; acceptance/durability/recovery semantics depend on the application's requirements.

These are readiness requirements and open design work, not implemented permissions, quotas, library security,
or an audit runtime. Native Core execution is not an OS sandbox. Kernel
[seccomp documentation](https://docs.kernel.org/userspace-api/seccomp_filter.html) explicitly distinguishes
system-call filtering from a complete sandbox; do not substitute a tool name for a threat model and evidence.
